# Architecture Risks

Status: PLANNED — a pre-implementation risk register. Revisit and update this document at the end of every phase in [roadmap.md](roadmap.md); a risk whose mitigation has clearly worked gets marked resolved rather than deleted (keeps the history honest).

Related: [implementation-blueprint.md](implementation-blueprint.md) · [../architecture/implementation-summary.md](../architecture/implementation-summary.md)

| # | Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|---|
| 1 | **Overengineering the agent framework before P6 proves it works.** Building a generic, pluggable "agent framework" (P5) speculatively ahead of having even one real agent can produce abstractions that don't fit the Recon Agent's actual needs. | High — wasted work, framework redesign mid-roadmap | Medium | Build the framework *against* the Recon Agent concretely (P5→P6 as one practical unit), not as an abstract exercise first. Do not generalize until a second agent (Vulnerability, P8) proves the abstraction actually fits two different shapes of work. |
| 2 | **Too many agents / artificial agent boundaries.** Seven agents plus the Orchestrator is already a lot of moving parts for an MVP; splitting further (e.g. a separate "Source Analysis Agent," flagged in the Contradictions section) would make the system harder to reason about without a matching gain in capability. | Medium — development and debugging overhead, unclear ownership | Medium | Keep the current seven-agent boundary as the ceiling for MVP. Any proposal for an eighth agent must show a responsibility the existing seven cannot express (per [implementation-blueprint.md §4](implementation-blueprint.md#4-agent-contracts))'s explicit "do not create agents merely because they sound architecturally attractive" rule. |
| 3 | **Excessive LLM dependence in stages that should be deterministic.** It would be easy, under schedule pressure, to let the Attack Graph or Risk Agent "just ask the LLM" instead of building the real deterministic engine — quietly reintroducing the non-reproducibility the architecture explicitly rejected (ADR-021). | High — breaks report defensibility, reintroduces hallucination risk into the project's core differentiator | Low (explicitly guarded against in docs) but **high cost if it happens**, so tracked anyway | Code review gate: the Attack Graph Agent and Risk Agent implementations must contain no LLM/provider call, period. Add this as an explicit, automated check (e.g. a lint rule or import-boundary test forbidding the LLM provider module from being imported into those two modules) rather than relying on review discipline alone. |
| 4 | **Unclear agent boundaries around "read-only re-check" vs. "validation check."** The Investigation Agent's read-only re-checks and the Validation Agent's non-destructive checks are conceptually different (per [../agents/investigation-agent.md](../agents/investigation-agent.md) and [../agents/validation-agent.md](../agents/validation-agent.md)), but an implementer under time pressure could blur them — e.g. letting Investigation's "re-request a page" capability quietly accept parameters that make it behave like a validation check. | Medium — would weaken the opt-in validation safety boundary without anyone deciding to weaken it | Medium | Implement the two as genuinely separate capability sets in the Tool Registry (different `requires_validation_mode` flag, different permitted-agent list), not as one parameterized capability two agents happen to call differently. The toolset-membership check in [../architecture/execution-model.md](../architecture/execution-model.md) is the enforcement point — test it directly. |
| 5 | **Database complexity creeping in via the `RiskAssessment` / `Finding.risk_*` overlap.** Flagged explicitly in [implementation-blueprint.md §3](implementation-blueprint.md#3-canonical-domain-model); if both are built "just in case," the system now has two sources of truth for a finding's current risk. | Medium — data integrity bugs, confusing queries | Medium (common failure mode when a review raises an entity that wasn't in the original data model) | Default to **inline fields on `Finding`** for MVP; do not create a `RiskAssessment` table until a concrete need for score history exists. Decision owner: whoever implements P13 confirms this in the phase report rather than silently building both. |
| 6 | **Event-model complexity outpacing actual need.** The event table in [implementation-blueprint.md §6](implementation-blueprint.md#6-event-model) lists 16 events; building a generic pub/sub event bus for all of them before anything consumes most of them in real time would be premature. | Medium — infrastructure built for a requirement (real-time UX) that MVP doesn't have | Medium | MVP persists events as rows (audit trail) and the dashboard polls; no message bus, no WebSocket server, until a specific feature needs sub-second updates. This mirrors ADR-005's existing "no Redis/queue reflex" reasoning, applied to events. |
| 7 | **Sandbox complexity blocking early phases.** A fully-hardened, network-policy-enforcing sandbox (non-root, read-only FS, per-tool-execution ephemeral containers, egress allow-listing) is a lot to build correctly before Phase P6 can even run its first real tool call. | High — could stall the whole roadmap at P4 | Medium-High | Build the sandbox in two honest tiers: a **minimal but correct** P4 version (subprocess isolation, timeout, no-shell, output caps — the properties that are safety-critical) and defer the stronger container-level hardening (dropped capabilities, read-only FS, egress allow-lists) to the hardening phase, as the original design already did (ADR-016, Phase 16 in the superseded `Phases.md`). Do not block P4 on building the *maximum* sandbox when the *minimum safe* sandbox is enough to proceed. |
| 8 | **Tool integration complexity — four scanner candidates for MVP is still a lot.** [../tools/scanners.md](../tools/scanners.md) lists Nmap, Nuclei, Semgrep, and Trivy as candidates; integrating all four before proving the pipeline works end-to-end would delay the vertical slice unnecessarily. | Medium — schedule risk, scope creep in P8 | Medium-High (natural tendency to "do all the tools") | The MVP vertical slice (blueprint §10) uses exactly **one** scanner integration. The other three are added one at a time, each as its own small, testable unit, only after the slice proves the architecture. |
| 9 | **Attack graph complexity — rule-set scope creep.** [../data/attack-graph.md](../data/attack-graph.md) lists nine relationship types (`EXPOSES`, `RUNS`, `AUTHENTICATES_TO`, `HAS_ACCESS`, `CAN_REACH`, `EXPLOITS`, `ESCALATES_TO`, `TRUSTS`, `LEADS_TO`); building rules for all nine before the engine itself is proven would be the same mistake as risk #8, applied to the graph. | Medium | Medium | P12 ships with the **minimal rule set** that makes the vertical slice's one finding class produce one correct edge (blueprint §10). Additional relationship types are added incrementally, each justified by a specific new finding/asset class the project is adding at that time — not pre-built speculatively. |
| 10 | **Frontend/backend coupling via premature API shape commitments.** Freezing exact response schemas for every endpoint in [implementation-blueprint.md §7](implementation-blueprint.md#7-api-surface) before any backend exists risks the frontend being built against a contract that has to change once real data shows its actual shape. | Low-Medium | Medium | OpenAPI generation (already decided for this project) makes this cheap to fix: the frontend's typed client is **generated from the backend's schema**, not hand-maintained — so a backend schema change propagates as a type error, not a silent drift. No action needed beyond following the existing decision. |
| 11 | **Unclear MVP boundary re-emerging per phase.** Even with blueprint §9 defined, there's a natural pull (visible in risks #8 and #9) to quietly expand "MVP" scope phase by phase ("just one more scanner," "just one more rule"). | Medium — the project never reaches a demonstrable end-to-end state | Medium-High (this is the single most common way portfolio/demo projects stall) | Treat [implementation-blueprint.md §9–§10](implementation-blueprint.md#9-mvp-definition) as the literal acceptance bar for "MVP done" — a phase report that adds scope beyond what §9/§10 require must say so explicitly and justify it, per [CLAUDE.md](../../CLAUDE.md)'s "phase discipline" rule, not drift into it silently. |
| 12 | **Reconciling "bounded agency" in practice, not just in docs.** The Guardrail §5 rewrite (ADR-021) is a sound policy, but policy text does not enforce itself — if the toolset-membership/intrusiveness/validation-gate checks in [../architecture/execution-model.md](../architecture/execution-model.md) are implemented loosely (e.g. checked in the agent's prompt instructions rather than in the Tool Registry code), an agent could still be talked into requesting something it shouldn't. | High — this is the project's central safety claim | Low-Medium (the design is sound; the risk is in implementation fidelity) | These three checks must be enforced in the Tool Registry's code path, independent of and prior to any LLM output — never as "the agent was told not to." Dedicated negative tests (per [../Decision.md](../Decision.md) ADR-015's safety-critical-code testing bar) must attempt to request an out-of-toolset / over-intrusive / validation-gated capability and assert refusal at the registry layer, not just check that the prompt says not to. |

## How to use this document during implementation

- Re-read this list at the start of each phase in [roadmap.md](roadmap.md) that a row above references, and treat the listed mitigation as an acceptance-criterion input, not optional advice.
- When a phase report is written, note which rows (if any) materialized despite mitigation, and what was done about it — this document should accumulate a track record, not stay static.
